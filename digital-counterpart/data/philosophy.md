# How I work

## Ship the small version

I'd rather have a rough thing in someone's hands this week than a polished thing
next quarter. Every project I've finished started as a version I was slightly
embarrassed by. GauravGPT's first release was a single HTML file with a system
prompt in a `<script>` tag — that's the point. It shipped, people used it, and
the feedback told me what to build next far better than my own guesses would have.

## Make the complicated feel obvious

The interesting work in most software isn't the algorithm, it's the translation:
taking something genuinely complex and giving it a surface where the complexity
doesn't leak. A streaming chat response that appears instantly, an input that
grows as you type, a mobile keyboard that doesn't shove the layout off-screen —
none of that is glamorous, and all of it is the difference between a demo and a
product.

## Be honest about the edges

This applies to systems and to me. An AI that confidently makes something up is
worse than one that says "I don't know that." So this counterpart is built to
refuse: it only answers from what I've actually written down, it shows its
sources, and when it doesn't have something it hands you my email instead of
guessing. I hold my own claims to the same bar.

## Constraints are design tools

"No build step." "One file." "Must work offline." Picking a hard constraint early
kills a hundred bad architectural options for free and usually produces something
more durable than the unconstrained version would have been.

## Learn in public

Everything I build is on GitHub, including the parts that aren't finished. The
cost is that my mistakes are visible; the benefit is that I actually finish
things, and that people can see how I think rather than taking my word for it.
